# Этап 05. Редактирование уже сохраненных записей

## Цель этапа

Дать пользователю контроль над качеством дневника после сохранения записи, чтобы ошибки можно было исправлять не только в моменте.

## Проблема сейчас

- После сохранения приема пищи пользователь фактически теряет возможность его исправить.
- Любая ошибка распознавания или подтверждения остается в данных и ухудшает доверие к аналитике.

## UX-spec

### Вход в сценарий

Пользователь открывает `История` -> `Приемы пищи` -> выбирает запись -> `Изменить`.

### Карточка сохраненной записи

Карточка должна содержать:

- название;
- время;
- калории и БЖУ;
- краткий состав или заметку, если есть;
- кнопки управления.

Кнопки:

- `Изменить название`
- `Изменить порцию`
- `Изменить время`
- `Изменить БЖУ`
- `Удалить запись`
- `Назад`

### Изменение записи

Поведение должно быть похоже на draft editing, но с явным подтверждением обновления:

```text
Изменения сохранены.
Обновленный прием пищи: курица с рисом, 480 ккал.
```

### Удаление записи

Удаление должно быть подтверждаемым:

```text
Удалить запись?
[Да, удалить] [Отмена]
```

После удаления пользователь должен получить:

- подтверждение удаления;
- обновленный дневной прогресс;
- путь назад в историю.

## Требования к UX/UI

- Редактирование сохраненной записи не должно отличаться по логике от редактирования черновика.
- Удаление должно быть защищено от случайного тапа.
- После изменений пользователь должен видеть, что аналитика пересчиталась.

## Задание для разработчика

### Что реализовать

1. Добавить сценарий открытия сохраненной записи из истории.
2. Реализовать редактирование основных полей сохраненной записи.
3. Реализовать удаление сохраненной записи с подтверждением.
4. Пересчитывать summary/decisions после изменений.
5. Обновить доступные действия после редактирования или удаления.

### Вероятные точки изменений

- `src/ai_me/telegram.py`
- `src/ai_me/services/health_service.py`
- `src/ai_me/storage/base.py`
- `src/ai_me/storage/memory.py`
- `src/ai_me/storage/mysql.py`
- `src/ai_me/domain/health.py` при необходимости
- `tests/test_telegram.py`
- `tests/test_health_service.py`
- `tests/test_mysql_store.py`

### Ограничения

- Не объединять этот этап с Mini App; редактирование должно быть доступно из чата.
- Если полный аудит истории изменений слишком дорог, можно оставить его на следующий этап, но итоговое состояние данных должно быть корректным.

## Критерии приемки

- Пользователь может открыть уже сохраненную запись.
- Пользователь может изменить минимум:
  - название;
  - время;
  - ключевые нутриенты.
- Пользователь может удалить запись после подтверждения.
- После изменения или удаления дневные метрики пересчитываются.
- Действия доступны через UI, а не только через внутренние ID и команды.

## Что проверить

### Автотестами

- открытие сохраненной записи;
- редактирование названия;
- редактирование времени;
- редактирование калорий/БЖУ;
- удаление записи с подтверждением;
- пересчет summary после обновления;
- пересчет summary после удаления.

### Вручную

- пользователь не боится исправлять запись;
- после правки видно новое итоговое значение;
- удаление не происходит случайно;
- сценарий не ломает историю и не оставляет пользователя без следующего шага.

## Definition of Done

Этап считается завершенным, когда пользователь может доверять дневнику как исправляемой системе, а не как одноразовому логу.
