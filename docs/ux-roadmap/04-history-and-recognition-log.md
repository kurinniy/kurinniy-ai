# Этап 04. История приемов пищи и история распознаваний

## Цель этапа

Дать пользователю возможность видеть недавние записи и возвращаться к ним без ощущения, что бот "забывает" прошлые действия.

## Проблема сейчас

- Пользователь не может посмотреть историю распознаваний.
- Нельзя быстро увидеть последние сохраненные приемы пищи.
- UX слишком одноразовый: отправил фото, ответ пришел, дальше контекст теряется.

## UX-spec

### Раздел "История"

Кнопка `История` открывает экран с двумя путями:

- `Приемы пищи`
- `Распознавания`

### История приемов пищи

Бот показывает последние 10 записей в обратном порядке:

```text
Последние приемы пищи:
12:40 • Курица с рисом • 420 ккал
09:10 • Омлет • 310 ккал
```

Для каждой записи доступны действия:

- `Открыть`
- `Изменить`

Если история длинная, нужен сценарий `Показать еще`.

### История распознаваний

Нужно показывать не только подтвержденные записи, но и историю работы с фото:

- `Сохранено`
- `Отклонено`
- `Ожидает решения`

Карточка должна включать:

- название/summary;
- время;
- confidence, если это полезно;
- статус;
- действие.

Для ожидающих распознаваний действия:

- `Сохранить`
- `Изменить`
- `Отклонить`

Для отклоненных:

- `Распознать заново` или `Создать вручную на основе этого фото`, если такой сценарий реализуется.

### Пустые состояния

Если данных нет:

- история приемов пищи: `Пока нет сохраненных приемов пищи. Отправьте первое фото еды.`
- история распознаваний: `Пока нет распознаваний. Просто отправьте фото еды в чат.`

## Требования к UX/UI

- История должна быть сканируемой, а не простыней текста.
- Пользователь должен различать:
  - сохраненные записи;
  - черновики;
  - отклоненные распознавания.
- Статусы должны быть написаны человеческим языком.

## Задание для разработчика

### Что реализовать

1. Добавить action `История`.
2. Реализовать два списка:
   - последние приемы пищи;
   - последние распознавания/черновики.
3. Добавить пагинацию или `Показать еще`, если элементов больше лимита.
4. Добавить действия из истории:
   - открыть;
   - перейти к редактированию;
   - сохранить ожидающий черновик;
   - отклонить ожидающий черновик.
5. При необходимости расширить store/service методами для выборки истории.

### Ограничения

- В этом этапе история может быть только по последним N элементам; полноценные фильтры и календарь остаются для Mini App.
- Не делать сложную аналитику внутри истории; здесь важны обзор и возврат к действию.

## Критерии приемки

- Пользователь может открыть историю из главного меню.
- Пользователь может посмотреть последние сохраненные приемы пищи.
- Пользователь может посмотреть историю распознаваний с понятными статусами.
- Из истории можно вернуться к действию, а не только читать список.
- Пустые состояния оформлены понятным человеческим текстом.
- История не требует знания внутренних ID.

## Что проверить

### Автотестами

- открытие раздела `История`;
- список последних приемов пищи;
- список последних распознаваний;
- корректные статусы элементов;
- `Показать еще` или пагинация;
- действия из списка.

### Вручную

- пользователь различает сохраненные, ожидающие и отклоненные записи;
- можно найти недавнюю запись без пролистывания большого числа сообщений;
- история не выглядит как техническая выгрузка;
- пользователь может продолжить незавершенный сценарий из истории.

## Definition of Done

Этап считается завершенным, когда у продукта появляется память о недавних действиях пользователя, доступная из чата.
