# AGENTS

## Правила работы

### Git

1. Сообщения коммитов писать на русском языке.

### Workflow

1. Каждую новую фичу делать в отдельной git-ветке.
2. Перед отправкой изменений проверять локальные тесты.
3. Новые фичи сначала проверять в staging-окружении.
4. Для staging использовать отдельного Telegram-бота и отдельную базу данных.
5. Только после успешной проверки в staging выкладывать изменения в production.
6. Изменения, связанные со схемой базы данных, сначала проверять в staging на реалистичных данных или сценариях.
7. Новые команды, кнопки и пользовательские сценарии Telegram сначала проверять только в staging-боте.
8. Для выкладки в staging использовать `bash scripts/deploy_stage.sh <feature-branch>` или `bash scripts/deploy_stage.sh`, если текущая ветка и есть фича.
9. Выкатка в staging считается завершенной только если скрипт сделал `git push origin stage` и локальный `stage` совпадает с `origin/stage`.
10. Не делать ручной `merge` в `stage` без последующего `push` и без `scripts/deploy_stage.sh`.

### Release

1. Каждый production-релиз обязан менять версию в `src/ai_me/version.py`.
2. Каждый production-релиз обязан менять `frontend/package.json`.
3. Для пользовательских фич повышать `MINOR`: `0.2 -> 0.3`.
4. Для багфиксов без новой функциональности повышать `PATCH`: `0.2.1 -> 0.2.2`.
5. Для production-релиза создавать git-tag версии в формате `vX.Y` или `vX.Y.Z`.
6. Версию, `frontend/package.json` и `CHANGELOG.md` обновлять на `main` в момент релиза, а не патчить для этого `stage`.
7. Для релиза использовать `scripts/release_main.py` или эквивалентный поток с теми же проверками.
8. Перед push релиза в `main` обязательно прогонять `release_guard` на итоговом release-коммите.
9. Если `release_guard.py` падает, релиз в `main` не делать.

### Changelog

1. Каждый релиз, выложенный в production, фиксировать в `CHANGELOG.md`.
2. Для каждого production-релиза указывать дату, commit и краткий список изменений.
